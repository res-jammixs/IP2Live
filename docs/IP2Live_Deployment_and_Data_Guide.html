Purpose and scope

Executive answer

IP2Live can run fully offline and now has a hardened Windows data design: core saves, progress snapshots, monthly attempt journals, and archived reports are written under %LOCALAPPDATA%\IP2Live, while IndexedDB and localStorage remain useful mirrors. The existing IP2Live-1.1-Windows folder is an older audit baseline and must be freshly exported and prepared before distribution.

Ready in source
Offline Windows persistence. Saves are atomic and integrity-checked, a verified backup is retained, reports are archived with SHA-256 sidecars, and telemetry is journaled before being mirrored to IndexedDB.
Offline by design
Local attempts and reports. Passed, failed, cancelled, interrupted, and detailed mistake events are retained locally. The default report window is 90 days, raw evidence is included, and PDF/XLS/JSON files are archived to the managed Reports folder.
Re-export first
The old Game.exe package is stale. It omitted all 11 custom music/effect assets. Create a fresh protected Windows export, run the supplied release-preparation script, then complete a clean-machine smoke test. A browser release still requires a separate web export.

The database question in one sentence

Putting the game online does not automatically require an online database. Keep IndexedDB if progress and reports may remain on one browser/device. Add a server database when you need accounts, cross-device continuation, centralized teacher reports, reliable backups, administrative dashboards, or authoritative assessment records.

Recommended release sequence

  1. Fresh Windows export: export again from RPG Paper Maker so the newly registered music and effects are embedded; do not distribute the stale IP2Live-1.1-Windows folder.
  2. Prepare and validate: run tools\prepare-windows-release.ps1 into a new destination. It installs the hardened host, synchronizes the plugin, excludes Git/developer saves, validates audio registrations, and writes a runtime hash manifest.
  3. Desktop production: smoke-test save/restart/backup recovery, every music zone, 90-day reporting, standard-user install, update, and uninstall; then sign and publish the ZIP or installer.
  4. Browser pilot: produce a separate RPG Paper Maker web export, clean it, test it from HTTPS, confirm report downloads and storage persistence, then publish as an itch.io HTML game or on a static web host.
  5. Online service: retain IndexedDB as an offline cache/outbox and synchronize events through an authenticated HTTPS API into a server database.

How to distribute the package correctly

  1. Make a release copy of the exported folder. Do not clean or alter the only master copy.
  2. Remove release-inappropriate content from the copy—at minimum resources\app\build\.git, .gitignore, and internal verification documents—then smoke-test.
  3. Keep every Electron runtime file and the entire resources and locales directories.
  4. Create one versioned ZIP, for example IP2Live-1.1-Windows-x64.zip.
  5. Tell users to extract the ZIP completely, then run Game.exe. Do not run it from inside the ZIP viewer.
  6. Publish a SHA-256 checksum and a short README with controls, minimum Windows version, report instructions, and support contact.
Do not ship the current export unchanged. It contains the project’s Git history inside resources\app\build\.git. That adds 459 files and about 41.3 MiB and may expose deleted or historical source content. Removing it also brings the game-content file count from 1,068 to 609.

Why there are three persistence layers

The app combines the RPG Paper Maker core save file with custom restore metadata and educational telemetry. IndexedDB is the correct layer for structured attempt history; localStorage is suitable only for the small snapshot map; the core save JSON is an engine requirement. The architecture is workable, but all three layers must be migrated and tested as a unit when packaging changes.

4. Does it record all attempts and export them?

Hardened answer: normal gameplay paths record starts, mistakes, and one terminal outcome; interrupted starts are preserved as unassessed evidence instead of disappearing. A forced power loss can still interrupt the final physical write in any local application, which is why the design uses an append-only journal, fsync, recovery, event IDs, and an audit sheet.

QuestionFinding
Are gameplay launches recorded?Yes. attempt_start is written when a gameplay node opens.
Are successes and failures recorded?Yes. Both close as attempt_end with passed/failed outcome and gameplay-specific metrics.
Are cancellations recorded?Yes. Cancellation closes an attempt_end marked cancelled and unassessed. Six previously wrong or missing gameplay cancellation paths were corrected.
Are mistakes/retries recorded?Yes where gameplay calls the central mistake handler. Raw attempt_mistake events and summarized retry/mistake data are supported.
Does the report show incomplete/crashed attempts?Yes. An orphaned attempt_start is reconciled as interrupted and remains unassessed; it is also visible in the raw Event Audit and JSON evidence.
What history is exported?The menu retains 7/30/90-day choices and defaults to 90 days. The durable journal is retained indefinitely by default, while the normal reporting guarantee is at least three months.
Is the latest event drained before export/quit?Yes during controlled export and quit paths. Pending journal and IndexedDB writes are awaited and storage failures fail the export instead of reporting false success.

What the report already provides

  • Player name, selected date window, generated date, sessions, active days, and play duration.
  • Gameplay instances, assessed attempts, passes, failures, cancellations, repetitions, rounds, retries, and mistakes.
  • Accuracy, completion rate, average/median/best completion time, trends, mastery indicators, competency summaries, and suggested intervention.
  • Attempt history with stage, level, map, quest, objective, gameplay, timing, outcome, recovery/rollback, security alerts, and evidence payload.
  • Daily, stage, quest, gameplay, competency, and step/mistake breakdowns.
Meaning of “all attempts.” The hardened event audit includes complete and interrupted attempts inside the selected window and archives raw JSON evidence. The menu intentionally promises a 90-day default rather than an all-time report. Local hashes detect accidental corruption; they do not make a learner-controlled device tamper-proof.

5. How capable is the app’s local storage?

For ordinary educational telemetry, capacity is not the limiting factor. IndexedDB is designed for structured, indexed datasets much larger than localStorage. The current records are JSON-like objects and should allow many thousands of attempts on a normal device. The bigger concerns are durability, identity, backup, and trust.

DimensionAssessmentRecommendation
Offline operationStrongKeep IndexedDB even if a server is later added; it supports offline-first play.
VolumeStrong for telemetryMonitor navigator.storage.estimate(); add retention/export only if actual usage grows unusually.
PersistenceStrong on hardened Windows; best-effort on webWindows uses managed files with backup recovery. Request persistent browser storage for a future web build.

Browser storage is origin-scoped and best-effort by default. Users can erase it, private browsing normally removes it at session end, and browsers may evict non-persistent data under storage pressure. Web Storage is commonly limited to about 10 MiB per origin, while IndexedDB receives a much larger browser-managed quota. These are reasons to keep high-volume telemetry in IndexedDB and small metadata only in localStorage.

7. Publishing the hardened game as an itch.io downloadable

Release preparation

  1. Export a fresh Windows build from the intended tagged source revision.
  2. Run tools\prepare-windows-release.ps1 with the fresh export as -SourceExportPath, a new empty destination, -ProjectRoot ., and the release version. Do not manually patch the export in place.
  3. Verify Game.exe starts on a clean Windows user account with no RPG Paper Maker installation.
  4. Create a profile, complete a pass, a failure, and a cancellation, save to a non-default slot, restart, load, and export both formats.
  5. Close the game, ZIP the whole folder, extract that ZIP to a new location, and repeat the launch/load test.
  6. Scan the release with current endpoint protection, calculate SHA-256, and archive the exact released ZIP and source tag.

itch.io page setup

  1. Create a project, choose Downloadable, and upload the ZIP directly or with Butler.
  2. Mark only Windows for this file, since that is the platform actually exported and tested.
  3. Provide version, approximate download/extracted size, 64-bit status if applicable, controls, save/report behavior, and known limitations.
  4. For private testing, keep the page restricted or use itch.io download keys. For a public release, add 3–5 screenshots and accurate metadata.
  5. For updates, keep the same project and Windows channel so players receive the new build through the itch app.

Butler workflow

butler login
butler push "C:\Release\IP2Live-1.1-Windows" YOUR_ACCOUNT/ip2live:windows

Butler accepts a directory or ZIP, creates compressed patch data, and efficiently uploads only changed content on later pushes. Its current uncompressed build limit is far above this game’s size. Do not place API credentials in source control or build logs.

Licensing check. RPG Paper Maker states that free use is for non-commercial releases and that commercialized games require its commercial license. Confirm the engine license and every font, audio, image, video, and third-party asset license before charging money, accepting revenue tied to access, or distributing commercially.

8. Google Drive and other direct-delivery methods

Direct links are technically sufficient because the build is self-contained. They are less convenient for updates, so use a disciplined release layout:

  • One immutable ZIP per version; never silently replace a file with different contents under the same filename.
  • A separate README.txt or landing page with “download → extract all → run Game.exe”.
  • Published SHA-256 checksum, file size, release date, change log, and support contact.
  • Read-only sharing permissions and a tested anonymous/student-access link.
  • A retention policy for older packages and a clear label for the currently supported version.
Update behavior. Hardened releases share %LOCALAPPDATA%\IP2Live, so installing or extracting a newer version elsewhere does not strand new-format saves or reports. The first hardened launch can import normal JSON saves found in its legacy build\Saves; moving from a different old portable folder still requires an explicit migration/backup step.

9. Windows installer plan

Installer readiness status

  1. Implemented — identity: the prepared package uses the stable product/package identity IP2Live and an isolated Chromium directory.
  2. Implemented — per-user data: saves, progress, telemetry, reports, and browser state live under %LOCALAPPDATA%\IP2Live, outside program files.
  3. Implemented — legacy core saves: first launch imports valid normal JSON slots found in the legacy build folder without deleting or overwriting the source. Back up and explicitly migrate the old generic %APPDATA%\game browser data if preserving a 1.1 profile history is required.
  4. Implemented — release hygiene: the preparation tool excludes embedded .git directories and developer save JSON, exactly synchronizes the current plugin, validates songs, and writes runtime hashes.
  5. Implemented — host hardening: renderer Node.js is disabled, context isolation and sandboxing are enabled, IPC is narrow and sender-validated, paths are never accepted from renderer storage calls, and unexpected navigation/popups are blocked.
  6. Still required — product release: configure the installer, test update/downgrade/uninstall policy, sign and timestamp the executable/installer, and verify on clean standard-user devices.

Pragmatic installer choice

Because RPG Paper Maker already produced a complete Electron directory, Inno Setup is a straightforward wrapper. NSIS is equally viable; MSIX offers stronger Windows integration but has stricter packaging rules. A per-user installer avoids an elevation prompt, but it does not remove the need to keep user data outside the application directory.

10. Updates, backups, and migration

Hardened-release manual backup

  1. Exit IP2Live completely so its journals and browser database are closed.
  2. Back up the whole %LOCALAPPDATA%\IP2Live directory. This contains saves, backups, progress, telemetry, report archives, and browser mirrors.
  3. Verify the copied save/report SHA-256 sidecars where applicable and protect the backup because reports contain identifiable performance information.
  4. For a one-time 1.1 migration, also preserve the old export's resources\app\build\Saves and %APPDATA%\game before changing identity.

Preferred future backup format

Add an in-game “Export My Data” command that creates one versioned bundle containing profile UUID, slot snapshots, engine save, telemetry event rows, schema version, export date, and a checksum. Add a matching import flow that validates the schema and shows a conflict preview.

Old profile-history migration is a separate operation. The prepared host intentionally stops using the collision-prone %APPDATA%\game identity. Preserve that directory before upgrading existing pilot users; the release tool migrates core JSON saves, not an arbitrary generic Chromium profile.

12. Browser and itch.io HTML deployment

Do not upload the Windows export as an HTML game. Its index.html is the renderer of an Electron app; the package uses a preload and window.ipcRenderer for desktop file I/O. Use RPG Paper Maker’s separate “Deploy for web browser” output.

Build and test workflow

  1. In RPG Paper Maker, export Deploy for web browser to a new empty directory.
  2. Confirm index.html is at the ZIP root, not inside an extra parent folder.
  3. Remove .git and internal files. Measure extracted size, individual file sizes, file count, and longest path.

13. What happens to IndexedDB when the game is online?

The same IndexedDB code can operate in a browser because it uses standard Web APIs. Its meaning changes:

  • Data belongs to the site’s origin—scheme, hostname, and port—not to an IP2Live account.
  • A different browser profile, computer, hostname, protocol, or port receives a different empty database.
  • Clearing site data, private browsing, storage pressure, browser policies, or corruption can delete it.
  • An itch.io game runs inside an iframe and browser privacy policies may affect third-party storage. Test the exact published page, not only localhost.
  • IndexedDB does not synchronize itself with a server database. Sync logic must be designed and implemented.

Local-only web hardening

  1. Call navigator.storage.persist() after explaining why persistence is useful.
  2. Show storage status and approximate usage from navigator.storage.estimate().
  3. Add full data export/import and an “erase my local data” control.
  4. Show a clear warning in private browsing or when persistence is unavailable.
  5. Use a stable production domain/origin and test data continuity across deployments.

Keep the client offline-first. Each event is saved locally first. A background sync worker sends pending events when connectivity is available. The API authenticates the player, validates the payload, assigns/accepts an idempotency key, stores the event once, and acknowledges it. The client then marks the outbox item synchronized.

Do not connect the game directly to the database

Database credentials embedded in JavaScript or an Electron renderer are recoverable by users. Place authorization, validation, rate limiting, data ownership checks, and schema evolution behind an HTTPS API or a managed backend that enforces equivalent server-side policies.

Deployment components

  • Static game host: itch.io HTML hosting or another HTTPS static/CDN host.
  • API: versioned endpoints such as /v1/events:batch, /v1/progress, and /v1/reports.
  • Database: relational storage is a strong fit because users, sessions, attempts, mistakes, stages, and reports have clear relationships.
  • Authentication: school SSO, managed accounts, or invitation codes mapped to immutable user IDs. Never use display name as identity.
  • Dashboard: separate teacher/admin web application with role-based access and server-generated reports.
  • Observability: service health and sync failure metrics without logging sensitive payloads unnecessarily.

Synchronization rules

  • Idempotency: server enforces uniqueness on eventId; retrying the same batch never creates duplicates.
  • Ordering: retain client timestamp and sequence, but also store server receipt time. Do not trust client clock for authorization.
  • Batching: send small batches, compress where supported, and back off after failures.
  • Append vs mutable: attempts/mistakes are append-only; progress snapshots are versioned and need conflict resolution.
  • Acknowledgement: remove nothing from the local outbox until the server confirms accepted event IDs.
  • Schema evolution: accept at least the current and previous event version during rolling updates.
  • Deletion: a server deletion request must also tell all signed-in clients to clear the corresponding local data.

17. Security, privacy, and trust boundaries

Desktop package

  • Keep external content out of the privileged Electron renderer. The current nodeIntegration: true/contextIsolation: false combination is acceptable only as a legacy local-content constraint, not as a pattern for loading remote pages.
  • Validate every IPC request, especially file paths. The current save IPC resolves a renderer-provided relative path against the app directory.
  • Remove DevTools shortcuts in production or gate them behind a deliberate support mode.
  • Use a current supported Electron line, track vulnerabilities, sign releases, and publish checksums.

Online service

  • HTTPS only; never ship database administrator keys in the client.
  • Use role-based authorization: student sees own records; teacher sees assigned groups; administrator scope is explicit and audited.
  • Validate sizes, types, allowed gameplay IDs, timestamps, and ownership on the server. Rate-limit event submission and report generation.
  • Encrypt data in transit and at rest, manage secrets outside source control, back up the database, and test restoration.
  • Collect the minimum necessary personal information. Define purpose, consent/notice, retention, correction, export, and deletion procedures before a school rollout.
  • Separate research analytics from operational records and de-identify exports where identity is unnecessary.
Trust statement. A PDF produced entirely from local IndexedDB proves what the local software reported, not that the data was never modified. For graded or compliance-sensitive use, generate the official report from authenticated server-received events and include report/audit identifiers.

Final recommendation

Release IP2Live first as a hardened Windows downloadable ZIP on itch.io. Create a fresh protected export so all custom audio is embedded, prepare it into a new destination with the supplied script, perform the clean-machine save/restart/report/music matrix, then sign and publish it. Google Drive is suitable for a controlled pilot mirror. The old screenshot build must not be distributed as the finished release.

For browser availability, make a separate RPG Paper Maker web export and initially keep IndexedDB local. Add a server database only when the product requirements include accounts, cross-device progress, central teacher visibility, reliable backup, or authoritative assessment. When that point arrives, do not discard IndexedDB: turn it into the offline event log and synchronization outbox behind an authenticated HTTPS API.
